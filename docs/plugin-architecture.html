1. 问题与目标

Jenkins 遇到未捕获异常时会生成一个 UUID 形式的 Logging ID，以 WARNING 级别打印 Caught unhandled exception with ID <uuid> 并附完整堆栈，同时在页面上提示用户去 System Log 里按这个 ID 搜索。

问题在于 System Log 页面由 RingBufferLogHandler 支撑，默认只保留 256 条记录。控制器日志一多，这条异常记录很快被轮转掉，用户按 ID 搜不到，只能登录服务器翻日志文件。

插件的目标很具体：

  • 在报错页（Oops 页）直接显示该 Logging ID 对应的完整日志，不再要求用户去别处搜索；
  • 提供一个独立的查询页，可以按 ID、异常、logger、关键字检索历史记录；
  • 捕获链路不依赖 System Log 的环形缓冲，不受其容量限制；
  • 日志内容只对管理员可见。

2. 整体结构

插件由两条链路组成：一条在服务端把异常记录截获并另存，另一条在浏览器端把记录取回并渲染。两者通过 Logging ID 关联，互不依赖对方的生命周期。

3. 扩展点与页面绑定

插件没有自己的注册表，也没有任何 XML 配置。它依赖两套机制：Jenkins 的注解发现（谁被实例化）和 Stapler/Jelly 的命名约定（URL 与页面如何找到 Java 方法）。这一节把这两条链路拆开讲。

3.1 用到的扩展点

扩展点实现类登记方式作用

3.2 注解如何变成实例

@Extension 不是运行期扫描注解，而是构建期生成索引。打开构建产物 logging-id.hpi，内层 jar 里有：

WEB-INF/lib/logging-id.jar!/META-INF/annotations/hudson.Extension
    io.jenkins.plugins.loggingid.LoggingIdAction
    io.jenkins.plugins.loggingid.OopsLogDecorator

WEB-INF/lib/logging-id.jar!/META-INF/annotations/hudson.Extension.txt
    （同上，供人阅读的文本副本）

这个索引由 maven-hpi-plugin 在打包时生成，Jenkins 启动后由 ExtensionList 通过 sezpoz 读取，按接口分类实例化：实现了 RootAction 的进入 RootAction 列表，继承了 PageDecorator 的进入 PageDecorator 列表。因此新增一个扩展点类不需要改任何配置文件，重新打包即生效。

索引里只有两个类，正好对应“一个 URL 入口 + 一个页面装饰器”；LoggingIdInitializer 不实现 Jenkins 接口，只靠 @Initializer 注解被初始化流程调用，所以不出现在这个索引里。

3.3 Jelly 视图如何被定位

Stapler 解析 URL 得到模型对象后，会在该对象所属类的包路径下找同名目录里的视图文件。产物中实际存在的只有两个视图：

io/jenkins/plugins/loggingid/LoggingIdAction/index.jelly
io/jenkins/plugins/loggingid/OopsLogDecorator/footer.jelly
URL / 触发点模型对象（it）视图渲染方式
/logging-id/ LoggingIdAction 实例 LoggingIdAction/index.jelly URL 末端就是对象本身，Stapler 取 index.jelly 渲染
/logging-id/log?id=… 同上，但命中 doLog 方法 无视图 方法直接返回 HttpResponse（纯文本 / 404）
任何使用 layout 的页面（含 Oops） OopsLogDecorator 实例 OopsLogDecorator/footer.jelly 由核心 layout.jelly 主动 st:include 进来

3.4 it.xxx 是怎么调到 Java 的

Jelly 里的 ${it.query} 这类表达式，会按 JavaBean 约定反射调用 getter：属性名首字母大写加 get，布尔类型优先找 is。插件里用到的对应关系如下。

模板写法实际调用说明
${it.permitted}isPermitted()决定是否渲染搜索区与表格
${it.query}getQuery()读 ?q= 并回填输入框
${it.levelFilter}getLevelFilter()读 ?level=，驱动下拉选中项
${it.entries}getEntries()搜索 + 级别过滤后的列表
${it.selected}getSelected()当前命中的单条，非空则渲染详情卡片
${it.maxEntries} / ${it.storedCount}getMaxEntries() / getStoredCount()页面顶部的容量与条数提示
${it.currentLoggingId}getCurrentLoggingId()装饰器从请求属性取当前 ID
${selected.exceptionType} 等LoggingIdEntry.getExceptionType() …详情与表格逐字段取用
安全性：两个模板首行都是 <?jelly escape-by-default='true'?>。这意味着 ${selected.text} 里的堆栈、${e.summary} 里的异常消息都会被自动 HTML 转义，异常内容不可能变成可执行脚本。这是“日志内容来自不可信输入”时的必要设置。

3.5 方法名如何变成 URL

Stapler 的方法派发规则是：URL 片段 log 对应 doLog()，参数用 @QueryParameter 从查询串绑定。

// GET /logging-id/log?id=3c68ac42-…
public HttpResponse doLog(@QueryParameter String id) { … }

另外三个方法是 RootAction 契约的一部分，不属于 Stapler 反射：

  • getUrlName() 返回 logging-id，决定挂载路径 /logging-id/；
  • getDisplayName() 返回侧边栏显示名；
  • getIconFileName() 返回 document.png，无权限时返回 null，侧边栏条目直接消失。

3.6 核心是怎么把 footer.jelly 拼进 Oops 页的

这是“页面和代码结合”最关键的一环。核心的 lib/layout/layout.jelly 在页脚处遍历所有 PageDecorator，并用 st:include 把各自的 footer.jelly 包含进来（optional="true" 表示没提供该视图的装饰器会被跳过）：

<footer class="page-footer jenkins-mobile-hide">
  <div class="page-footer__flex-row">
    <div class="page-footer__footer-id-placeholder" id="footer"></div>
    <j:forEach var="pd" items="${h.pageDecorators}">
      <st:include it="${pd}" page="footer.jelly" optional="true" />
    </j:forEach>
    …

三点直接结论：

  • it="${pd}" 把 it 绑定成装饰器实例，所以模板里才能写 it.currentLoggingId；
  • footer.jelly 会在每一个 layout 页面被调用，不只是 Oops 页——因此模板必须用 <j:if test="${loggingId != null}"> 自限；
  • 包含点是 page-footer__flex-row 这个 flex 容器，这正是当初 <details> 被排成左右两列、日志看起来被截断的根因，也是后来改用 fixed 悬浮的直接原因。

而 Oops 页本身（jenkins/model/Jenkins/oops.jelly）使用标准 layout，并把 ID 写进页面：

<l:layout title="Jenkins" type="one-column">
  <l:header />
  <l:main-panel>
    …
    <p>Logging ID=${request2.getAttribute('jenkins.exception.id')}</p>

这个属性由核心的 InstallUncaughtExceptionHandler 在捕获异常时写入请求。插件的装饰器读的是同一个属性，因此面板上的 ID 与页面正文里的 ID 必然一致，不需要额外的上下文传递。

3.7 三条完整调用链

场景链路
查询页渲染 GET /logging-id/?q=… → RootAction 实例 → LoggingIdAction/index.jelly → getQuery() / getEntries() / getSelected() → store.search() / store.resolve()
Oops 面板 核心渲染 oops.jelly → layout.jelly 遍历 PageDecorator → st:include it=pd page=footer.jelly → getCurrentLoggingId() → 输出面板 → 浏览器 fetch /logging-id/log?id=… → doLog() → checkPermission → HttpResponses.plainText

5. 捕获与存储：LoggingIdStore

5.1 为什么不用 System Log

System Log 的环形缓冲大小由核心配置决定，默认 256 条，且是所有日志共享的一个窗口。插件如果要“保证能查到”，就不能寄生在这个窗口里，必须自己持有一份独立存储。这也是整个插件最核心的取舍。

5.2 单例与安装时机

存储是进程级单例，用静态内部类 Holder 实现懒加载。构造时完成三件事：确定容量、创建 LinkedHashMap、安装 CaptureHandler。

maxEntries = Math.max(1, Integer.getInteger(
        LoggingIdStore.class.getName() + ".maxEntries", 200));

容量默认 200，可用系统属性 io.jenkins.plugins.loggingid.LoggingIdStore.maxEntries 覆盖（下限 1）。

LoggingIdInitializer 用 @Initializer(after = InitMilestone.PLUGINS_STARTED) 主动触发一次单例初始化，这样即使插件是在运行中被动态加载的，Handler 也会尽快挂上；同时任何代码路径第一次调用 LoggingIdStore.get() 时也会懒加载兜底。

5.3 Handler 如何过滤

CaptureHandler 被添加到 JUL 的根 logger 上，级别设为 ALL。每条 LogRecord 只做一次正则匹配：

Pattern.compile("Caught unhandled exception with ID ([0-9a-fA-F-]{36})")

只有命中这个格式的记录才会被转成 LoggingIdEntry 并入表，其余日志直接丢弃。这样既不会把根 logger 变成第二个全量日志收集器，也避免了额外的内存开销。

健壮性：publish() 内部捕获了所有 RuntimeException。诊断插件绝不能因为自身异常干扰 Jenkins 的日志输出——这是插件类代码的底线。

5.4 淘汰策略与并发

底层是 Collections.synchronizedMap(new LinkedHashMap<>(16, 0.75f, false))，访问序关闭、保持插入序，重写 removeEldestEntry 在超过容量时淘汰最旧的一条。

protected boolean removeEldestEntry(Map.Entry<String, LoggingIdEntry> eldest) {
    return super.size() > maxEntries;
}

这里用 super.size() 而不是 size() 并非风格问题：在匿名子类里直接写 size() 会被 SpotBugs 判为 IA_AMBIGUOUS_INVOCATION_OF_INHERITED_OR_OUTER_METHOD（外层与继承方法的调用歧义），CI 会因此直接失败。

读取时先复制一份值集合再反转（最新在前），复制在 synchronized (entries) 内完成，避免遍历时被写入干扰。

5.5 两种查找语义

方法语义用途
get(id)精确匹配内部按 ID 取单条
resolve(query)先精确，再唯一前缀匹配；前缀命中多条则返回 null支持从截图里抄了一半的 ID
search(query)大小写不敏感子串匹配，范围覆盖 ID、消息、logger、堆栈、级别查询页关键字搜索

6. Oops 页面板：OopsLogDecorator

6.1 注入点

Jenkins 的 oops.jelly 使用标准 <l:layout>，因此 PageDecorator 是最干净的扩展点——不需要改核心模板。插件只提供 footer.jelly，它会在所有使用 layout 的页面被渲染，所以模板里先做一层判断：

<j:set var="loggingId" value="${it.currentLoggingId}"/>
<j:if test="${loggingId != null}"> … </j:if>

getCurrentLoggingId() 从请求属性 jenkins.exception.id 读取，这个属性只在错误分发时由核心写入，所以面板天然只出现在 Oops 页。

6.2 一个必须绕开的坑：Oops 页是匿名上下文

关键事实：Oops 页由容器的 error dispatch 渲染，不经过安全过滤器，请求在这些过滤器眼里始终是匿名的。因此在 footer.jelly 里用 hasPermission(ADMINISTER) 决定“要不要显示日志”永远为假，面板会整体消失。

由此形成最终方案：

  • 面板只渲染 Logging ID（ID 本身不是敏感信息）；
  • 日志正文由浏览器带着自己的会话 Cookie 请求 /logging-id/log?id=…；
  • 权限校验放在那个端点里，用真实会话判断；匿名请求得到 403。

6.3 布局：为什么是 fixed 悬浮

核心页脚是 flex 行布局。最初把 <details> 直接嵌进去，结果 summary 与 <pre> 被排成左右两列：标题被挤成窄条，正文从面板中间开始并溢出到屏幕右侧，看起来像日志被截断。

最终改为：面板 position: fixed 脱离页脚流，内部自己用纵向 flex 排版——标题栏独占一行（align-self: stretch 撑满宽度），正文 flex: 1 1 auto 占满剩余空间并在面板内滚动。宽度取 min(1100px, calc(100vw - 2em))，既接近满宽又不贴边。

width: min(1100px, calc(100vw - 2em));
max-height: 70vh;
display: flex; flex-direction: column;
overflow: hidden;

6.4 前端取数逻辑

面板通过 data-log-url 暴露地址，页面加载后 fetch 一次，按状态码给出不同文案：

状态面板显示
200完整日志文本，同时显示 Copy 按钮
403“Sign in as an administrator to view this log.”
其他非 2xx“No captured log for this ID. It may have been evicted or Jenkins may have restarted.”
网络异常“Failed to load the log. Use the Logging ID page instead.”

Copy 按钮默认隐藏，拿到正文后才出现，避免复制到占位文案。

7. 查询页与日志端点：LoggingIdAction

7.1 路由与权限

RootAction 挂在 /logging-id/，显示名 “Logging ID”，图标 document.png。getIconFileName() 在无权限时返回 null，侧边栏链接对普通用户直接不出现。

public HttpResponse doLog(@QueryParameter String id) {
    Jenkins.get().checkPermission(Jenkins.ADMINISTER);
    LoggingIdEntry entry = store.resolve(id);
    if (entry == null) {
        return HttpResponses.notFound();
    }
    return HttpResponses.plainText(entry.getText());
}

同一个端点承担两个用途：Oops 面板的 fetch，以及查询页“Download full log”的下载链接（浏览器按 download 属性存成 logging-id-<id>.txt）。

7.2 页面数据来源

模板不直接访问存储，而是通过 Action 的 getter 取值，查询参数就地解析：

Getter来源说明
getQuery()?q=关键字或 Logging ID
getLevelFilter()?level=空 / WARNING / SEVERE
getEntries()store.search + 级别过滤无权限时返回空列表
getSelected()store.resolve(query)命中则渲染详情卡片
getStoredCount() / getMaxEntries()存储元信息页面顶部显示“当前 X 条 / 上限 Y 条”

7.3 页面构成

  • 搜索区：文本框 + 级别下拉 + Search 按钮，GET 提交，参数直接体现在 URL 上，便于收藏或转发。
  • 统计行：保留上限、当前条数、匹配条数；并明确提示“记录不跨重启持久化”。
  • 详情卡片（当 q 命中时）：时间、级别、logger、异常类型、根因（最内层 Caused by:）、复制按钮、下载链接、完整堆栈。
  • 记录表格：时间、Logging ID（可点击回到详情）、级别、异常类型、消息摘要。ID 单行显示，异常列允许换行，避免省略号截断。

7.4 LoggingIdEntry 的派生字段

字段生成方式
timeyyyy-MM-dd HH:mm:ss.SSS，系统默认时区
summary消息首行，超过 200 字符截断加省略号
exceptionType堆栈首行（异常类名 + 消息）
rootCause遍历堆栈取最后一条 Caused by:，即最内层原因
text“时间 级别 logger + 消息 + 堆栈”的纯文本，供复制/下载/面板渲染

8. 运行时数据流

  1. 内核捕获未处理异常，生成 UUID，以 WARNING 打印 Caught unhandled exception with ID … 并附堆栈。
  2. CaptureHandler 匹配到 ID，把记录转成 LoggingIdEntry 存入内存表。
  3. 容器渲染 Oops 页，footer.jelly 从 jenkins.exception.id 拿到 ID，输出悬浮面板与 data-log-url。
  4. 浏览器 fetch 该地址（携带会话），端点校验 ADMINISTER 后返回纯文本。
  5. 面板把文本写入 <pre>，显示 Copy 按钮；查询页则通过 /logging-id/ 提供历史检索。

9.2 verify 阶段做了什么

mvn verify 在打 hpi 之外还会依次执行 license、hpi、spotbugs、spotless 等绑定在 verify 上的检查。也就是说：本地 mvn package 成功不代表 CI 会过——第一版就是在 package 阶段通过、在 verify 阶段被 SpotBugs 拦下的。

9.3 测试

LoggingIdActionTest 用 JenkinsRule 起真实实例，共 3 个用例，加上插件父 POM 自动注入的 6 个校验用例，合计 9 个：

  • capturesAndRendersLoggingId：手工打印一条带 ID 的 WARNING，访问 logging-id/?q=<id>，断言页面包含 ID、异常消息、异常类名与根因。
  • servesRawLogTextForOopsPanel：请求 logging-id/log?id=<id>，断言返回的纯文本包含 ID 与异常消息。
  • rendersEmptyState：无记录时页面仍正常渲染，包含标题与容量提示。

10. 部署与运维

当前调试实例是 WSL 中的 Jenkins（127.0.0.1:8080），插件以 hpi 形式直接放入插件目录：

cp target/logging-id.hpi /var/lib/jenkins/plugins/logging-id.hpi
chown jenkins:jenkins /var/lib/jenkins/plugins/logging-id.hpi
systemctl restart jenkins
为什么不走上传接口：该实例上 /pluginManager/uploadPlugin 会返回 500，根因是 Jenkins 2.528.3 自身的 doUploadPluginImpl 抛出 IndexOutOfBoundsException（与 crumb 无关），因此改为直接落盘 + 重启。

运维上需要知道的三点：

  • 记录只存内存，重启即清空，不落盘、不跨节点；
  • 只捕获内核未捕获异常处理器打印的记录，普通 WARNING 不会进入；
  • 日志正文仅管理员可取，普通用户最多在报错页看到一个 ID。

11. 限制与取舍

限制原因 / 取舍
重启后记录丢失刻意不持久化：避免磁盘写入、脱敏与清理问题，与 System Log 行为保持一致
最多 200 条异常记录带完整堆栈，体积不小；200 条足够覆盖“最近一次排查”的窗口，可用系统属性调整
只匹配固定句式依赖核心 Caught unhandled exception with ID … 的格式；核心若改文案需要同步调整正则
匿名访问只能看到 IDOops 页走 error dispatch，安全过滤器不参与，无法在渲染期判断身份；权限校验后移到数据端点
面板遮挡页面内容悬浮面板换取了“不破坏页脚布局”的稳定性；宽度与最大高度都做了上限
